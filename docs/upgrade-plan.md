# 功能升级与改造路线

以下为依据现状提出的建议，尚未执行功能改造，也未确定业务排期。

## 建议顺序

| 优先级 | 改造项 | 理由 | 完成标准 |
| --- | --- | --- | --- |
| P0 | 建立现状人工验收记录 | 先获得后续改造可对照的行为基线 | 按验收清单记录环境、结果及问题 |
| P0 | 明确图集描述文件用途 | manifest 与运行时规格不一致，易导致素材替换错误 | 明确每个描述文件对应资源；更新生成流程和文档后再调整运行时 |
| P1 | 分离内容与交互 | 详情内容内嵌于 main.js，编辑文案需要改交互文件 | 独立内容文件，保持五个详情入口与文本安全渲染 |
| P1 | 降低 DOM 和事件耦合 | 两个脚本共享元素与事件，命名变化易引入回归 | 统一初始化边界、事件定义及必要节点缺失时的处理 |
| P1 | 整理 CSS 层叠与设计变量 | 基础样式与末尾覆盖共存，后续视觉调整成本高 | 合并重复规则、保留现有断点及焦点/减少动效行为 |
| P1 | 增加有价值的非 UI 检查 | 当前 check 仅验证语法 | 静态资源引用、内容键匹配、图集尺寸及构建输出有可重复检查 |
| P2 | 作品内容深化 | 当前仅提供介绍弹窗 | 按真实材料补充角色、问题、方案、结果及可公开链接 |
| P2 | 独立作品地址与分享 | 当前详情没有独立路由或 URL 状态 | 明确采用 hash 还是静态详情页，支持直接访问及返回行为 |
| P2 | 分享与搜索元信息完善 | 已有 description、OG 标题/描述，分享图等仍可完善 | 使用确认的域名和真实图片补充元信息，检查链接有效性 |

P2 内容需有真实资料支撑，不编造项目成果、数据、联系方式或外链。若新增表单、数据采集或后台，再单独确定数据流、权限、存储与服务边界。

## 实施拆分

1. 记录基线：当前版本、人工验收结果、必须保留的内容与交互。
2. 每次选一个目标：先拆内容，再调整模块，最后进行视觉或功能扩展，便于定位回归。
3. 内容拆分时同步调整脚本加载方式；若使用 ES module，明确导入路径和初始化顺序。当前构建只复制文件，不转译、不打包。
4. 宠物改造先固定资源格式和状态语义，再调整状态机、绘制与交互。保持失败时的静态猫图和关键词整理能力。
5. 每次变更运行适用检查，并由用户完成 UI 验收；文档中同步更新功能表与事件契约。
6. 如需发布，另行获得外部发布授权，并准备可恢复的上一版静态产物。

## 主要风险

- 修改 HTML ID、data-open 或作品 key 时，需同步 main.js 的查询和 entries。
- 修改脚本顺序、异步初始化或事件监听时，需确认事件不会在消费者注册前丢失。
- 拖拽、点击抑制、pointercancel 与焦点恢复相互关联，不能只检查鼠标点击。
- 减少动效、手动暂停、隐藏页面和离屏是不同状态，应分别验证。
- 图集路径、尺寸及行列语义必须一起处理；重新生成素材后不能默认兼容现有 frame 映射。
- `dist` 是可重建产物，改源码后再构建；不要将已有本地未提交改动当作可随意覆盖的历史基线。

## 单项升级需求模板

```text
名称：
用户与场景：谁在什么情况下需要它？
现状问题：可复现的行为或明确缺口。
目标行为：触发条件、正常结果、失败/取消结果。
范围：涉及哪些入口、内容、模块及资源？
兼容约束：移动端、键盘、减少动效、素材失败。
内容来源：文案、图片、链接及可公开范围。
验收条件：可逐项判定的结果。
自动化检查：适用的语法、逻辑或构建检查。
人工 UI 验收：由用户记录环境与结果。
发布与恢复：发布目标、授权及上一版恢复方式。
```
